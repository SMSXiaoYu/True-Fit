# 二期（MVP后优化）

## 1. Source 粒度优化

### 问题

当前 source 用粗粒度（W1/W2/P1/P2），导致：

1. **跨 group 内容重叠**：G1、G2、G3 都引用 W1，导致同一事实（支付回调、对账、大促）出现在多个 group 里
2. **LLM 无法细分**：拿到 W1 = 整段工作经历，无法区分里面的不同主题
3. **悬停高亮是"一大段对一大段"**：用户悬停瘦身简历的一句，原文对应的是整段（如整个 W1），不是对应的那几句。理想体验是"短句对短句"。

### 根因

调用1的 `source` 字段用了粗粒度编号（W1），不是句子级（W1_L3）。

为什么当初选粗粒度：v8 定稿时为了切分稳定性，放弃了细粒度。

### 解决方案

调用1改用句子级 source（W1_L3、P1_L5）。

### 代价

- 调用1要重跑
- 切分稳定性可能下降（需要重新验证）
- 整个 pipeline 的 source 体系要改
- 前端悬停高亮的"粒度"会变细（从段落级→句子级），用户体验提升

### 优先级

二期，不是 MVP。

MVP 可接受：内容重叠不影响事实，用户可手动删；高亮粗一点不影响功能。

## 2. 内容维度标定

### 问题

embedding 算出的内容分，区分度低：
- 最相关（E1）：6.0
- 最不相关（E8）：4.8
- 差距只有 1.2 分

### 根因

同语言同域文本，bge-m3 的余弦相似度天然偏高，都在 0.48-0.60 区间。

### 两种标定方案（都有缺陷）

| 方案 | 做法 | 缺陷 |
|---|---|---|
| A 固定参数 | (sim - 0.4) / (0.75 - 0.4) | 过拟合，换数据失效 |
| B 动态标定 | (原分 - min) / (max - min) | 相对分，最不相关的=0分，失真 |

### 一期处理

不标定，接受内容分挤在 4.8-6.0。

靠其他维度（技能、资历）拉开差距，加权后仍能分层。

### 二期方向

- 换更好的 embedding 模型（区分度更高）
- 或做「绝对分 + 相对分」双轨
- 或引入校准样本集（已知相关/无关的样本，算基线）

### 优先级

二期，不是 MVP。

## 4. 剩余时间动态估算

**问题：**

提取过程（第1步到第2步之间）的“大概还剩：约 X 分钟”，当前是固定值。

**目标：**

根据“每步平均耗时”动态估算。

**实现思路：**

- 记录每次 pipeline 各步骤的实际耗时（存到 meta.json 或日志）
- 累计多次后，算出“每步平均耗时”
- 前端根据当前步骤 + 平均耗时，动态显示剩余时间

**优先级：**

二期。

## 5. 提取速度优化

**问题：**

首次提取约 110 秒，其中：
- step1（简历提炼）：中
- step2（JD提炼）：小
- step5（改写指令生成）：大，约 60 秒

**优化方向：**

1. **调用1和调用2并行**：两者互不依赖，可同时跑，省约 20-30 秒
2. **精简 step5 的 prompt**：当前 prompt 较长，可能影响速度
3. **step5 流式输出**：边生成边渲染，用户感知更快（但实现复杂）

**优先级：**

二期。

## 2.用户数据收集（第二批）

**背景：**

第一批数据（性能 / 质量 / 输入特征）已在二期完成。
第二批是“用户行为数据”，需要前端埋点。

**要收集的数据：**

| 数据 | 用途 |
|---|---|
| 用户编辑率 | 衡量 AI 初稿质量 |
| 编辑距离（改了多少字） | 同上 |
| 重新生成率 | 用户不满意的频率 |
| 导出率 + 导出格式偏好 | 用户满意的信号 |
| 页面停留时长 | 哪步最耗时 / 最纠结 |
| 回退步骤 | 哪步最容易出错 |
| 配置调整频率 | 用户在意哪些参数 |
| 拖拽次数 + 删除模块数 | AI 初稿的“冗余度” |
| 上传到生成的时间 | 用户操作习惯 |
| 回访率 | 产品粘性 |

**为什么放远期：**

1. 需要前端埋点（改动大）
2. 涉及用户隐私，需要用户系统 + 用户同意
3. 没有真实用户前，数据量不够分析

**前提：**

- 有用户系统（登录 / 匿名 ID）
- 有隐私政策
- 有数据存储（数据库）

### 3.OCR 识别（图片/扫描版文件）

**背景：**

当前只支持“文字版 PDF / Word”的解析。
如果用户上传的是：
- 扫描版 PDF（图片）
- 截图（如从 BOSS 直聘截图的 JD）
- 拍照的简历

系统解析不了。

**要做什么：**

对图片/扫描版文件，做 OCR 识别，转成文字。

**技术方案（三种）：**

| 方案 | 做法 | 成本 |
|---|---|---|
| A | 前端 OCR（tesseract.js） | 免费，但慢、精度一般 |
| B | 后端 OCR（PaddleOCR） | 精度高，但要部署 |
| C | 第三方 API（百度/腾讯/阿里） | 精度最高，但花钱 |

**优先级：**

远期。

**理由：**

1. 不是核心场景（大部分用户上传的是文字版文件）
2. 成本高
3. 有替代方案（用户可先手动复制粘贴）

## 4. 新增【科研】预设（拓展垂直领域）

**问题：**

当前的四大预设（通用、技术、管理、校招）主要针对企业侧的常规招聘（如互联网、金融、传统行业等）。但对于投递高校教职、科研院所、博士后或企业研发中心（R&D）的候选人来说，评估维度大不相同。科研岗位更看重论文/专利产出、课题级别、研究方向与实验室的契合度，而非纯工程落地或管理能力。

**解决方案：**

在配置面板的【预设系列】中增加【科研】选项。
- 分数分配倾向：大幅提升【内容】（论文/课题描述）与【资历】（学历/科研年限）的权重，降低【行业】权重。
- 维度判定特化：在调用1（简历提炼）和调用2（JD提炼）中，针对科研岗位特化提取“发表论文数”、“影响因子”、“科研项目级别（国家级/省级）”等专用字段。

**优先级：**

远期（新方向，需独立验证科研类 JD 与简历的数据表现）。

## 5. 本地化部署大模型（隐私强化与降本）

**问题：**

简历和 JD 包含了大量用户的个人隐私（姓名、电话、公司内部机密项目等），尽管协议声明会保护隐私，但上传到云端 API 始终是阻碍部分高端用户使用的门槛。且随着用户量增加，云端 API 的调用成本（调用1/2/X/5 均需消耗 Token）会急剧上升。

**解决方案：**

提供“本地模型”选项。
1. **轻量级本地推理**：在用户本地电脑运行轻量级开源模型（如 Qwen2.5-7B、Llama-3-8B），用于处理轻量任务（如调用2 JD提炼、调用X 句组切分）。
2. **端侧隐私保护**：用户的简历和 JD 根本不离开本地电脑。
3. **成本打平**：引导不想付费 Pro 版的免费用户使用本地模型。

**技术方案：**
- 集成 Ollama 或 LM Studio 的本地 API，让 TrueFit 前端/轻量后端直接请求 `http://localhost:11434`。

**优先级：**

远期。


## 6. 简历从零构造（引导式访谈生成）

**背景与痛点：**

当前 TrueFit 解决的是“有简历，如何精简/匹配”的问题。但大量应届生或跨行者面临的最大痛点是**“无从下笔”**——他们有经历，但不知道怎么写；或者只有零散的日记、流水账，甚至只是一段口头陈述。

**解决方案：**

新增【简历构造】模块，作为 TrueFit 的上游。重点打造**“引导式提问”**与**“低门槛交互”**，帮用户把口头故事变成标准简历。

### 核心交互设计（重中之重）

1. **引导式提问与即时确认（Prompt 核心设计）**
   - **不问大词，只问场景**：直接问“你的职责是什么”用户会卡壳。必须采用 STAR 法则引导，问具象化的场景。例如：“在这段经历中，你**最有成就感**的一件事是什么？”“当时遇到了什么**棘手的问题**？你用了什么**工具/方法**解决的？”“最终达成了什么**数字结果**？”
   - **动态追问（深层挖掘）**：如果用户答“我负责了订单开发”，AI 必须追问：“是重构还是新增？耗时降低了多少？用了什么技术栈？”
   - **用户编辑与确认（核心原则）**：AI 提取出的每一条经历或技能，都必须在右侧预览区生成可编辑的卡片。用户必须能**随时点击修改、拖拽调整顺序、或直接删除** AI 的提取结果。最终点击【确认并生成】时，这份简历才真正定型。
   - **宽容度**：允许用户“想到哪说到哪”，AI 负责将其拆解为“基本信息、教育、技能、Action（动作）、Result（结果）”。

2. **双模态交互（打字与语音）**
   - **打字模式（适合安静环境）**：采用“左聊天，右预览”的布局。右侧实时渲染简历草稿，左边对话。
   - **语音模式（主打解放双手，拒绝打字）**：接入前端语音转文字（如 Web Speech API 或微信原生语音）。用户可以按住录音，像跟 HR 打电话一样聊自己的经历，系统自动转文字并结构化。

### 演进路线

1. **阶段一：长文本一键结构化（极简版）**
   - 不搞多轮对话，用户直接给一段【个人陈述】（流水账/大纲均可）。
   - 调用 LLM 将其一次性拆解为标准简历格式（填充到现有的第 5 步模型里）。
   - **用户进入现有的第 5 步（确定其他信息）和最终完成页，可自由修改并导出。**
   - 用户可无缝衔接现有的 TrueFit 瘦身流程。
2. **阶段二：对话式 AI 访谈（终极版）**
   - 实现上述的“双模态交互 + 动态追问 + 实时编辑确认”。
   - 引入多轮记忆与冲突处理（如用户前面说 5 年经验，后面说 2 年，AI 会反问澄清）。

**优先级：**

远期（新方向）。这是与“精简”并行的另一条独立产品线（从 0 到 1 的构建），交互复杂度极高，建议在当前的瘦身 MVP 完全验证跑通后再启动。
