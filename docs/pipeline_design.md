# 调用链设计（Pipeline Design）
## 0. 定位
从简历原文到瘦身简历的完整生成链路。
串联 5 个调用 + 1 个用户交互环节 + 1 个规则生成环节，同时实现 Source Mapping 和相关性引擎。
## 1. 总览

简历原文 + JD原文  
↓  
[调用1] 简历提炼 → experiences JSON  
[调用2] JD提炼 → requirements JSON  
↓  
[调用3] 四维度打分 → 每条经历的分数  
[调用4] 分层（质量+硬信号+阈值） → 每条经历的 tier  
↓  
[环节U] 用户选择 + 聚类  
├─ 模式A：用户勾选 + 手动聚类  
└─ 模式B：系统自动全选 + 自动聚类  
↓  
[调用5] 改写指令生成 → changes 数组  
↓  
[环节G] Gate 1-4 校验 + 执行  
↓  
瘦身简历 + Source Mapping  
↓  
[调用6] 匹配报告生成（规则，不调LLM）  
↓  
匹配报告（总体分 + 结论 + 命中/缺口 + 改动说明 + 补充建议）  
↓  
[调用7] 组装完整简历（纯规则）  
↓  
完整简历 + 匹配报告


## 2. 调用清单

| # | 环节 | 类型 | 输入 | 输出 |
|---|---|---|---|---|
| 1 | 简历提炼 | LLM | 简历原文 | experiences JSON |
| 2 | JD提炼 | LLM | JD原文 | requirements JSON |
| 3 | 四维度打分 | 规则+embedding | experiences + requirements | 每条经历4维度分数 |
| 4 | 分层 | 纯规则 | 分数 + 硬信号 | 每条经历 tier |
| U | 用户选择+聚类 | 交互 | 分层结果 | 选中的经历 + 聚类分组 |
| 5 | 改写指令生成 | LLM | requirements + experiences + tier + 聚类 + 授权operation | changes 数组 |
| G | Gate 1-4 校验 | 本地规则 | changes + source_store | 校验后的最终输出 + mapping |
| 6 | 匹配报告生成 | **纯规则** | 分数 + 命中项 + 缺口项 + changes | 匹配报告 |
| 7 | 组装完整简历 | 纯规则 | 调用1产物 + 调用5产物 | 完整简历 |

## 3. 每次调用的详情

### 调用1：简历提炼

- **输入**：简历纯文本原文
- **输出**：完整对象（resume_id / basic_info / intent / education / certificates / skills_declared / experiences / source_store / source_map）
- **Prompt要点**：
  - 按“业务主题”切分经历单元，跨章节合并、去重
  - 切分规则：业务主题合并 / 独立项目 / 通用职责不单独成E / 跨章节合并
  - 字段规则严格遵守
  - 不新增原文没有的内容
- **稳定性验证**：
  - A简历：3次8段，切分一致（1次9段，小波动）
  - B简历：3次5段，边界有差异（可接受）
  - C简历：3次5-7段，数量有差异（可接受）
  - **结论：切分不强制100%稳定，接受“合理初稿 + 用户手动调整”**
- **版本**：v8 定稿

---

### 调用2：JD提炼

- **输入**：JD纯文本原文
- **输出**：requirements JSON（含 hard / skills / responsibilities / industry / level + source_store + source_map）
- **Prompt要点**：
  - 按5维度提取：硬性条件 / 核心技能 / 核心职责 / 行业领域 / 资历层级
  - weight 判断规则：熟练/熟悉→high，了解→medium，优先/加分→low+bonus
  - responsibilities 拆分规则：逗号分隔的并列动作拆条
  - industry 不推断，JD没写填 null
  - source_map 无来源用空数组 `[]`
  - 编号规则：D=Duty / R=Requirement / B=Bonus
- **稳定性验证**：10/10/10（3次输出完全一致）
- **版本**：v2 定稿

---

### 调用3：四维度打分

- **输入**：experiences JSON + requirements JSON
- **输出**：每条经历的4维度分数（技能 / 内容 / 行业 / 资历，各0-10）
- **算法**：
  - **技能**：三级兜底
    - 第1级：tech 字段匹配
    - 第2级：tech 命中率<0.5 → actions 补抽
    - 第3级：仍<0.5 且该经历是技术岗 → skills_declared 兜底
    - 技术岗判断：role含技术词 / industry技术相关 / tech非空
  - **内容**：JD responsibilities vs 经历 actions，embedding 语义相似度（bge-m3）
    - 算法：每条 responsibility 和每条 action 算余弦相似度，取每条 responsibility 的最高相似度，求平均 × 10
    - 模型：bge-m3（本地，CPU）
    - 性能：JD职责向量只编码一次，8段经历复用
    - 已知问题：相似度区间窄（4.8-6.0），区分度不够，二期做标定
  - **行业**：JD industry.required vs 经历 industry；JD无要求时中性化给5
  - **资历**：JD level.years vs 经历 seniority，规则判断
  - **加权**：技能20% / 内容45% / 行业15% / 资历10%
- **验证结果**：
  - 行业、资历：100%一致
  - 内容：偏差0.2
  - 技能：三级兜底后，偏差消除
  - **排序完全一致，分层可靠**
- **版本**：已定稿

---

### 调用4：分层

- **输入**：每条经历的4维度分数 + 硬信号列表 + 权重配置
- **输出**：每条经历的 tier（核心内容 / 相关内容 / 其他内容）
- **算法**：
  1. 4维度加权 → 原总分
  2. 算质量分 → 调整内容分 → 重算总分
  3. 判断是否命中硬信号 → 总分加分（每个+1.5，上限+3）
  4. 按阈值分层（≥7核心 / 4-7相关 / <4其他）
- **验证结果**：100%一致（技能兜底后）
- **版本**：已定稿

---

### 环节 U：用户选择 + 聚类

- **类型**：用户交互，不是LLM调用
- **输入**：调用4的分层结果 + 卡片列表
- **输出**：选中的经历 + 聚类分组

**两种模式：**

| 模式 | 选择 | 聚类 |
|---|---|---|
| 模式A 自定义 | 用户勾选 | 用户手动（拖拽合并 / 勾选合并） |
| 模式B 一键 | 系统全选 | 系统自动（按主题合并） |

**交互细节：**
- 卡片按相关度分从高到低排序
- 可勾选 / 删除（进已删除区，可恢复）/ 拖拽调序 / 合并
- 合并后：actions / results 合并，tech 去重

**输出给调用5：**
- 选中哪些经历
- 每段经历的聚类分组
- 合并后的 actions / tech

---

### 调用5：改写指令生成

- **输入**：
  - requirements JSON
  - experiences JSON（含 tier + allowed_operations + original_texts）
  - 用户聚类结果
- **输出**：changes 数组（每条含 output_id、operation、source_ids、text、reason）
- **Prompt要点**：
  - 输出的是改写指令，不是简历文本
  - 硬性规则：只压缩/重排/换措辞、数字必须来自原文、贡献动词不升级、source_ids 不能为空、无法改写时用 verbatim
  - 严格 JSON schema，固定 operation 枚举
  - 头尾都有任务说明
  - 按用户聚类分组生成
  - merge/compress 边界：不同 member → merge；同一 member → compress
  - 输出风格：简历书面语，禁止第一人称和口语词
- **稳定性验证**：
  - 格式：5/5
  - operation：4/5（G1有分裂，可接受）
  - source_ids：3/5（部分group数据不完整，可接受）
  - text：4/5
  - 事实可追溯：靠 Gate 4 兜底
- **版本**：v5 定稿

---

### 环节 G：Gate 1-4 校验

- **类型**：本地规则，不是LLM
- **输入**：changes 数组 + source_store
- **输出**：校验后的最终输出 + mapping_table

**四道门禁：**

| 门禁 | 检查 | 不通过处理 |
|---|---|---|
| Gate 1 | source_ids 必须真实存在 | 拒绝该条 |
| Gate 2 | 公司名/时间/职位不能被改 | 拒绝该条 |
| Gate 3 | operation 在允许列表内 | 拒绝该条 |
| Gate 4 | text 里的数字、贡献动词、事实性名词，必须能在原文找到 | 回退原文 |

**验证结果**：4/4 通过

---

### 调用6：匹配报告生成

- **类型**：纯规则，不调LLM
- **输入**：分数 + 命中项 + 缺口项 + changes
- **输出**：完整匹配报告

**报告包含6块：**

| 块 | 来源 | 方式 |
|---|---|---|
| 总体匹配分 | 算法 | 直接取 |
| 一句话结论 | 规则 | 模板（3种情况 + 边界） |
| 四维度分数 | 算法 | 直接取 |
| 命中项 | 规则 | JD要求 vs 简历证据匹配 |
| 缺口项 | 规则 | JD要求 - 简历命中 |
| 改动说明 | changes | operation + reason拼接 |
| 补充建议 | 规则 | 模板 + 缺口项 + 特殊项 |

**命中项的显示口径（随内容维度算法切换）：**
- 如果内容是 embedding 算法，命中项显示「最高相似度 + 最匹配的 action」
- 如果是关键词算法，命中项显示「命中关键词」

**一句话结论的3种模板：**
- 有优势无短板："{优势}命中度高，整体匹配良好，建议直接投递。"
- 有优势有短板："{优势}命中度高；{短板}存在明显缺口，建议按补充建议微调后投递。"
- 无优势有短板："{短板}存在明显缺口，建议按补充建议补强后再投递。"
- 边界：各维度表现均衡，整体匹配良好，建议直接投递。

**版本**：已定稿

---

### 调用7：组装完整简历

- **类型**：纯规则，不调LLM
- **输入**：
  - 调用1产物的 basic_info / intent / education / skills_declared
  - 调用5改写后的经历
- **输出**：完整简历（可直接投递）
- **组装方式**：
  - 基本信息 / 求职意向 / 教育经历：原文照搬
  - 技能清单：按JD相关性排序，不删
  - 经历：调用5的改写结果，按核心/相关/其他分层
- **版本**：待实现

## 4. 调用之间的数据衔接

- 调用1 → 调用5：experiences 传递
- 调用2 → 调用5：requirements 传递
- 调用3 → 调用4：分数传递
- 调用4 → 环节U：tier 传递
- 环节U → 调用5：选中的经历 + 聚类分组 传递
- 调用5 → 环节G：changes 数组传递
- 环节G → 调用6：校验后的 changes + source_store
- 调用3/4 → 调用6：分数 + 命中项 + 缺口项
- 调用6 → 输出：匹配报告
- 调用1 → 调用7：basic_info / intent / education / skills_declared
- 调用5 → 调用7：改写后的经历
- 调用7 → 输出：完整简历

## 5. Source Mapping 的埋点

- 调用1：简历提炼时，每个字段记录 source（粗粒度 W1/P1）
- 调用2：JD提炼时，每个要求记录 source（D/R/B）
- 调用5：每条 change 绑定 source_ids + operation
- 环节G：写入 mapping_table，校验 source_ids 真实性

## 6. 相关性引擎的接入点

- 调用3：算四维度分数（含技能三级兜底）
- 调用4：质量调整 + 硬信号 + 分层
- 调用5：按 tier 和聚类结果决定 allowed_operations

## 7. 异常处理

| 环节 | 异常 | 处理 |
|---|---|---|
| 调用1/2 | 失败 | 提示用户重新上传 |
| 调用3/4 | 失败 | 兜底给默认分层 |
| 调用5 | 失败 | 回退 verbatim |
| Gate校验 | 失败 | 回退原文 |
| 调用6 | 失败 | 用默认模板兜底 |
